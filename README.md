# 📱 Mr Center — تطبيق أندرويد لإدارة السناتر التعليمية

تطبيق احترافي كامل (Android الآن، ويُبنى لـ iOS بنفس الكود لاحقاً) يعمل على **نفس قاعدة بيانات Supabase**
المرتبطة بموقع الويب الحالي — فأي بيان تُسجّله من التطبيق يظهر في الموقع والعكس، لأن الاثنين يقرآن
ويكتبان في نفس الجداول.

> المشروع مبني بـ **React Native (Expo) + TypeScript + Supabase** ومصمم بالكامل بالعربية RTL
> بتدرجات لونية حديثة وشاشات احترافية لكل قسم.
>
> 🤖 **لوكيل الذكاء الاصطناعي الذي سيعمل على المشروع**: ابدأ بقراءة [`AGENTS.md`](AGENTS.md) —
> المرجع الكامل الذي يشرح كل شيء حرفياً (الرؤية، المعمارية، قاعدة البيانات، الممنوعات، الاختبارات).

## ✨ أهم المميزات

| الميزة | الوصف |
|---|---|
| 🏢 **تعدد السناتر** | كل سنتر له بياناته المعزولة تماماً بعمود `center_id` وسياسات أمان (RLS) على الخادم |
| 🔑 **كود السنتر الفريد** | صاحب السنتر يختار كوداً (3–8 حروف/أرقام) عند التسجيل — **ثابت وفريد**، ولو مكرر تظهر «الكود غير متاح» |
| 👥 **3 صلاحيات** | سوبر أدمن (أنت — المطور) / مسئول سنتر (مدير أو مدرس) / طالب — لكلٍّ واجهته وصلاحياته |
| 🔒 **حسابات فريدة** | البريد ورقم الهاتف **فريدان على مستوى النظام كله** حتى لو السنتر مختلف — برسالة واضحة «مستخدم من قبل» |
| 🔗 **ربط تلقائي** | الطالب يكتب كود السنتر **مرة واحدة فقط** عند التسجيل، وبعدها حسابه مرتبط بسنتره تلقائياً عند كل دخول |
| 🛠 **لوحة تحكم المطور المخفية** | لا تظهر لأي أحد غيرك: الاشتراكات، إيقاف/تفعيل السناتر، محتوى «حول التطبيق»، مفاتيح التجربة |
| ☁️ **كلاود فلير وسيط مركزي** | التطبيق يسأل عامل Cloudflare عن مفاتيح قاعدة البيانات عند كل تشغيل — تغيّرها من لوحة Cloudflare (Supabase أو أي منصة) فتتبعها كل الأجهزة تلقائياً خلال دقيقة |
| 🔄 **تحديث ذاتي للتطبيق** | ترفع APK جديداً على Cloudflare R2 وتزيد رقم الإصدار ← كل جهاز يكتشف التحديث، يحمّله ويثبّته فوق القديم (مع وضع إجباري اختياري) |
| 💳 **الاشتراكات** | شهري / سنوي / مخصص — تتحكم في كل سنتر (تفعيل، تجديد، إيقاف) وشاشة حظر تلقائية عند الانتهاء |
| 🗂 **أقسام كاملة** | طلاب، مجموعات، صفوف، حضور، مدفوعات ومستحقات، درجات، إعلانات، ملف شامل لكل طالب |

## 🚀 خطوات التشغيل (بالترتيب — اتبعها حرفياً)

### 1️⃣ تجهيز قاعدة بيانات Supabase

افتح مشروع Supabase المرتبط بموقعك الحالي (نفس المشروع) ثم:

1. افتح **SQL Editor** ← **New query**
2. انسخ كامل محتوى ملف [`supabase/android_multitenant_schema.sql`](supabase/android_multitenant_schema.sql)
3. الصقه واضغط **Run**
4. ستظهر `Success` — وهذا ما فعله الملف:
   - أنشأ جداول: `centers`, `profiles`, `center_subscriptions`, `app_config`
   - على **قاعدة جديدة فارغة**: أنشأ أيضاً جداول الموقع المشتركة كاملة
     (`grades`, `groups`, `students`, `dues`, `payments`, `sessions`, `attendance`,
     `announcements`, `manual_grades`...) — وعلى قاعدة الموقع القائمة يتخطى الموجود تلقائياً
   - أضاف عمود `center_id` لجداول الموقع (**بيانات الموقع الحالية لا تتأثر إطلاقاً**)
   - أنشأ دوال التسجيل الآمن وسياسات العزل الكاملة

> ⚠️ **مهم جداً**: حساب الموقع الحالي (حسابك القديم كمدرس) يظل يعمل بصلاحية كاملة تلقائياً
> — النظام يتعرف عليه بأنه «بدون ملف شخصي» فيمنحه وصولاً كاملاً. **لا تنشئ ملفاً شخصياً (profile) لحساب الموقع القديم.**
> ⚠️ وبعد تشغيل هذا الملف، **لا تُعِد تشغيل** ملف `schema.sql` القديم الخاص بالموقع؛ فهو يعيد السياسات
> الواسعة القديمة. (عند ترقية الموقع لاحقاً سيُبنى على هذا المخطط الجديد.)

### 2️⃣ ضبط المصادقة (Authentication)

في لوحة Supabase:

1. **Authentication → Sign In / Providers → Email**
2. **فعّل** «Allow new users to sign up» — لأن أصحاب السناتر والطلاب سيسجلون حساباتهم من التطبيق
   > (ملحوظة: موقع الويب القديم كان يطلب إيقافها لأنه أحادي المستخدم؛ التطبيق متعدد المستخدمين
   > والحماية الآن تأتي من سياسات RLS والصلاحيات، وليس من إيقاف التسجيل.)
3. **أبقِ** «Confirm email» **مفعّلاً** — لمنع الإيميلات الوهمية؛ التطبيق يحفظ التسجيل معلقاً على الجهاز
   ويُستكمله تلقائياً عند أول دخول بعد تأكيد البريد (التدفق مشروح في AGENTS.md)

### 3️⃣ إنشاء حسابك كمطوّر (سوبر أدمن)

1. في Supabase: **Authentication → Users → Add user → Create new user**
   - بريدك الشخصي + كلمة مرور قوية، وفعّل **Auto Confirm User**
2. انسخ **UID** الخاص بالمستخدم ثم نفّذ في **SQL Editor**:

```sql
INSERT INTO public.profiles (id, role, full_name, email)
VALUES ('الصق-الـ-UID-هنا', 'super_admin', 'المطور', 'بريدك@mail.com');
```

3. احفظ بريدك وكلمة مرورك لنفسك — **لا يظهر زر دخول المطور لأي مستخدم آخر أصلاً** (شرح الدخول بالأسفل).

### 4️⃣ ربط التطبيق عبر كلاود فلير (المعمارية الجديدة)

التطبيق **لا يحتاج مفاتيح مدمجة** — بل يسأل **عامل Cloudflare** عن مفاتيح قاعدة البيانات
عند كل تشغيل، وهو نفسه يجيب أيضاً عن «هل يوجد إصدار أحدث من التطبيق؟».

```
التطبيق ──يسأل──▶ عامل Cloudflare ──يرد──▶ { مفاتيح قاعدة البيانات + آخر إصدار }
                      ▲
                أنت تتحكم فيه من لوحة Cloudflare (تغيير القاعدة أو إصدار تحديث)
```

1. أنشئ العامل وارفع ملف [`cloudflare/worker.js`](cloudflare/worker.js) —
   **الدليل الكامل خطوة بخطوة في [`cloudflare/README.md`](cloudflare/README.md)**
2. ضع مفاتيح Supabase في قسم `DATABASE` داخل العامل ← Deploy
3. ضع رابط العامل في `app.json` ← حقل `extra.configUrl` قبل بناء التطبيق
4. (اختياري) للتحديث الذاتي: أنشئ bucket في R2 لاستضافة ملفات APK — مفصّل في نفس الدليل

> 💡 **تغيير قاعدة البيانات مستقبلاً لأي منصة أخرى**: تعدّل قسم `DATABASE` في العامل فقط ←
> كل الأجهزة تلتقط الجديد تلقائياً. ويمكنك أيضاً من لوحة المطور داخل التطبيق إدخال
> «مفاتيح يدوية للتجربة» على جهازك قبل نشرها للجميع.
>
> 🔁 **إصدار تحديث**: ترفع APK الجديد إلى R2 وتزيد `latest_version` و`version_code`
> في العامل ← التطبيق يكتشفه تلقائياً ويعرض «ما الجديد» ثم يحمّل ويثبّت فوق القديم
> (مع خيار `force_update` لجعل التحديث إجبارياً).

### 5️⃣ تشغيل التطبيق وتجربته على هاتفك

```bash
npm install
npx expo start
```

- ثبّت تطبيق **Expo Go** من متجر Play على هاتفك
- امسح **QR Code** الظاهر في الطرفية ← يفتح التطبيق فوراً على هاتفك للتجربة

### 6️⃣ بناء ملف APK/AAB موقّع بشهادة (للتوزيع والنشر)

البناء يتم عبر خدمة Expo السحابية المجانية (EAS) — وهي **تنشئ وتدير شهادة التوقيع (Keystore) تلقائياً**:

```bash
npm install -g eas-cli
eas login                 # حساب Expo مجاني
eas build --platform android --profile preview      # ملف APK للتثبيت المباشر
eas build --platform android --profile production   # ملف AAB لرفعه على Google Play
```

- بعد انتهاء البناء (دقائق) تحصل على رابط تحميل مباشر للملف الموقّع
- الشهادة تُحفظ مشفّرة في حسابك على EAS وتُستخدم في كل بناء لاحق — نفس الشهادة دائماً
  (وهذا **شرط أساسي** ليعمل التحديث الذاتي: الـ APK الجديد يُثبَّت فوق القديم فقط إذا كان بنفس الشهادة)
- بعد توزيع أول نسخة APK: ارفع تحديثاتك اللاحقة إلى **Cloudflare R2** وحدّث أرقام الإصدار
  في العامل — الأجهزة ستحدّث نفسها تلقائياً (الدليل: [`cloudflare/README.md`](cloudflare/README.md))
- لبناء نسخة iOS لاحقاً: `eas build --platform ios` (تحتاج حساب مطور Apple، والتحديث الذاتي أندرويد فقط)

## 🎮 خريطة استخدام التطبيق

### الصفحة الرئيسية (ترحيبية)
- **إنشاء حساب سنتر جديد** — لصاحب السنتر/المدرس (يختار كود سنتره الفريد الثابت هنا)
- **تسجيل طالب جديد** — يدخل كود السنتر أولاً فيرى اسم سنتره للتأكيد، ثم يكمل بياناته
- **دخول مسئول السنتر** / **دخول طالب** — تسجيل دخول بالبريد وكلمة المرور فقط (بلا كود)

### 🕵️ دخول لوحة تحكم المطور (مخفية عن الجميع)
**ضغطة مطوّلة (٣ ثوانٍ) على شعار التطبيق** في الصفحة الرئيسية ← بوابة خاصة ← ادخل ببريد المطور وكلمة مروره.
لو دخل أي شخص آخر بنفس الطريقة بحسابه العادي ستظهر له «منطقة محظورة». من اللوحة تتحكم في:

| القسم | ما تفعله |
|---|---|
| مفاتيح الربط | عرض مصدر الاتصال الحالي (كلاود فلير) + إدخال «مفاتيح يدوية للتجربة» على جهازك قبل نشرها على كلاود فلير |
| إدارة السناتر | عرض كل السناتر وأكوادها وعدد طلابها + **إيقاف/تفعيل** أي سنتر فوراً |
| الاشتراكات | تفعيل/تجديد باقة (شهرية/سنوية/مخصصة بأي مدة) أو إيقافها لأي سنتر |
| حول التطبيق | تعديل اسم التطبيق ووصفه وبيانات التواصل ورسالة عامة — تنعكس فوراً للجميع |

> تغيير قاعدة البيانات وإصدار التحديثات لكل العملاء يتم من **لوحة Cloudflare** (العامل + R2) —
> انظر [`cloudflare/README.md`](cloudflare/README.md).

### لوحة مسئول السنتر
الرئيسية (إحصائيات حية) · الطلاب (إضافة/تعديل/بحث/ملف شامل) · المجموعات (أيام ومواعيد ورسوم) ·
الحضور (تسجيل بضغطة: حاضر/متأخر/غائب) · المزيد: المدفوعات (توليد مستحقات شهرية + تحصيل)، الإعلانات، الصفوف، الإعدادات والاشتراك.

### تطبيق الطالب
الرئيسية (ترحيب + مجموعتي + الإعلانات) · سجل حضوري · درجاتي بمتوسط عام · مدفوعاتي (معلق/مسدد) · حسابي (بياناتي وسنتري وكوده).

## 🔐 ملاحظات أمنية

- **كل العزل يتم على الخادم** عبر Row Level Security — وليس داخل التطبيق؛ فحتى لو تلاعب أحد
  بالتطبيق لن يقرأ بيانات سنتر آخر، لأن قاعدة البيانات نفسها ترفض.
- الطالب لا يرى إلا سجلاته هو (الحضور/الدرجات/المدفوعات) وبيانات سنتره العامة (الإعلانات/المجموعات).
- مسئول السنتر لا يرى ولا يعدّل إلا بيانات سنتره، وعند إيقاف سنتره يُمنع من الكتابة على مستوى الخادم.
- كود السنتر **وحالة إيقاف السنتر** محميان بمشغّل قاعدة بيانات: لا يغيّرهما إلا المطور —
  فلا يستطيع مسئول سنتر إعادة تفعيل سنتره بنفسه بعد إيقافه.
- الصلاحية (role) وربط الطالب بسنتره محميان بمشغّل: لا يغيّرهما المستخدم مهما كان.
- **حساب موقع الويب القديم**: عند تشغيل المخطط تُسجَّل كل حسابات المصادقة الموجودة لحظتها
  تلقائياً في «القائمة البيضاء للنظام القديم» (`app_config ← legacy_admins`) فيحتفظ أصحابها
  بصلاحية كاملة، بينما يمرّ أي حساب يُنشأ بعد الترحيل إجبارياً عبر نظام الصلاحيات —
  ولا يمكن لأي مسجّل جديد ادعاء صلاحية المالك. لإضافة حساب قديم لاحقاً:
  ```sql
  UPDATE public.app_config
     SET value = value || '"<UID-الحساب>"'::jsonb
   WHERE key = 'legacy_admins';
  ```
- مفتاح `anon` المعروض آمن — الحماية كلها في سياسات RLS (نفس مبدأ موقعك الحالي).

## 🔗 عن ترقية موقع الويب لاحقاً

- الجداول والأعمدة **نفسها** بين الموقع والتطبيق (students, groups, attendance, payments...) مع إضافة `center_id` فقط.
- ترقية الموقع لاحقاً = تجعل استعلاماته تملأ/تصفّي بـ `center_id` وتستخدم تسجيل الدخول الجديد (profiles) —
  وحينها سيُقرأ كل ما أنشأه التطبيق فوراً لأنه في نفس الجداول أصلاً.
- بيانات الموقع الحالية (قبل الترقية) تظل `center_id = NULL` وتخص حساب الموقع القديم، ويمكن للمطور
  إسنادها لسنتر لاحقاً بتحديث عمود `center_id` من لوحة SQL.
